# 画质增强方案（Android 阅读器）

> 2026-10-30 ｜ 状态：**已决策 —— 不做**（2026-10-30 决定）｜ 全部结论基于真实漫画页实测
>
> **本文作为决策记录保留**：以后再有人提「给阅读器加画质增强」，先读这里，不要重测一遍。
> 一句话理由：真实漫画页宽 1040，手机 fit-width 只需 1.04×，正常阅读根本不存在"糊"；
> 只有双指放大才有差异，而两条路分别受限于「收益太小」（双三次 +14.5%）和
> 「会改内容」（AI 超分 +140%，但网点/拟声字被重画）。
>
> 本文经过两次修正。第一版基于合成样张，得出「AGSL cubic 值得做」；用真实漫画页（黑杰克 01）
> 复测后**推翻了那个结论**——合成样张把收益夸大了约 4 倍。

## 1. 结论

1. **正常阅读（fit-width）不需要任何画质增强。** 真实漫画页宽 1040，1080 屏只需放大 **1.04×**，
   四种方案肉眼与像素都无差别。
2. **只有双指放大到 2× 以上才存在"糊"**，此时：
   - 双三次 / AGSL cubic：边缘提升 **+14.5%**，代价几乎为零，但改善有限；
   - AI 超分（Real-ESRGAN / Real-CUGAN）：边缘提升 **+140%**，观感质变，但**会重画内容**
     （网点被当成色块重建），且要算力。
3. **服务端做增强不划算**：+143ms/页、+40% 流量，换来的画质还不如客户端 cubic。
4. **`filterQuality` 换档完全无效**，见 §3.1，别再试。

**建议**：暂不实现。若要做，只做「放大时的可选增强」，默认关，让用户选保真还是观感。

## 2. 素材与场景

测试素材：`怪医黑杰克01.pdf`（157 页扫描件），已放入 `.dev-comics/`（gitignore，不进库）。

| 项目 | 数值 |
|---|---|

## 3. 实测记录

### 3.1 `FilterQuality` 是空档（已证实）

**静态证据**：`ui-graphics 1.7.5` 的 `AndroidPaint_androidKt.setNativeFilterQuality`：

```java
paint.setFilterBitmap(filterQuality != FilterQuality.None)
```

四档塌缩成一个布尔值。整个 `ui-graphics` 里没有 `SkSamplingOptions` / `CubicResampler` ——
Android 后端走 `android.graphics`，平台层没有三次/Lanczos 重采样 API。

**实测**（探针已随决策删除，结论保留）：`FilterQualityProbeTest`（900×200 噪声 → 1050×233）：

```
low / medium / high → md5 faec19fca17c14889b201048b8d2af14（同一个哈希）
none                → md5 85516d6215b0668287eae69fb4166b1f
```

网上（含多个技术站点的教程）说"改成 High 就能显著提升清晰度"是错的。

### 3.2 真实页 1.04×：四行无差别

四行对照探针（双线性 / 原图 1:1 / cubic 直接入层 / cubic 原生入层，已删），
目标宽 1080、源宽 1040：**四行肉眼与像素都看不出区别**。

原因很简单：1.04× 的放大，任何插值核都等于没做。

### 3.3 真实页 2.08×：才有差异，且指标要选对

裁一块 520 宽的区域按 1080 渲染（等价双指放大 2.08×）：

| | 全局标准差 | 梯度能量 | 强边缘占比 |
|---|---|---|---|
| 双线性 | 67.6 | 10.06 | 2.86% |
| AGSL cubic（原生入层） | 68.8（+1.8%） | **11.52（+14.5%）** | **3.31%（+16%）** |

**全局标准差是错指标**——漫画大片留白，差异只在边缘，用 std 会被稀释到看不出。
评漫画放大的锐度要用**梯度能量 / 强边缘占比**。

### 3.4 AI 超分的上限（Real-ESRGAN ncnn，同一块区域 2×）

| | 梯度能量 | 强边缘占比 |
|---|---|---|
| 双线性 | 8.44 | 1.41% |
| 双三次 | 10.12 | 2.90% |
| **Real-ESRGAN（animevideov3）** | **20.20** | **8.58%** |

梯度 2.4×、强边缘 6×，和插值不是一个量级。**代价是内容被重画**：西装格子纹理被画成块状图形，
不是原图网点结构；拟声字/小字也有改形风险。

耗时：1040×1387 → 2080×2774，**1.2s/页**（RTX 4060 Ti，含 PNG 编码）。

### 3.5 AGSL 的结构限制（决定了它跑不了完整 Anime4K）

Anime4K v4 结构：`Upscale_CNN_x2_VL` = **18 pass**，`Restore_CNN_S` = **4 pass**，
每 pass 一层 3×3 卷积（`mat4` 权重 4 通道），层间有**残差**（`result + MAIN`）和跳连。

`RenderEffect.createChainEffect(e1,e2)` 里每层只能拿到**上一层**输出，拿不到更早的图层 ——
残差表达不了。实测（4 pass 串链、省略残差，仅测耗时）：

| | p90 | p95 | p99 |
|---|---|---|---|
| 双线性 | 19 | 19 | 30 |
| AGSL cubic（1 pass） | 21 | 22 | 32 |
| 4 pass 卷积 | 23 | 27 | 46 |

要跑真 Anime4K 只能走 JNI + GLES 自管 ping-pong FBO 那条路。

> 附：我在 PC 上用真 OpenGL 复刻了 mpv 的 shader 宿主（脚本已删），
> `Restore_CNN_S` 跑通（0.02s），但 `Upscale_CNN_x2_VL` 的 depth-to-space pass 依赖 mpv 精确的
> `_pos/_size/_pt` 语义，两次尝试分别产出竖条纹和退化输出，**数据作废**。
> 连在条件最好的环境里复刻宿主都这么麻烦，这也侧面说明 AGSL 那条路不可行。

### 3.6 服务端传统增强（纯 Go，未接路由）

合成页 900→1080：

| 方案 | 耗时 | 体积 | 梯度/std |
|---|---|---|---|
| 基线 `MakeThumb` | 20ms | 63KB | — |
| Lanczos3（不锐化） | 108ms | 90KB | std 100.9 |
| **CatmullRom + USM 0.4** | 163ms | 88KB | std 110.2 |

真实页 1040→2160（2.08×）：双线性 129ms / CatmullRom 217ms / +USM0.4 490ms / +USM0.8 476ms，
std 73.1 / 73.9 / 74.5 / 75.1。

**两个结论**：Lanczos3 与已有 CatmullRom 画质打平且慢 1.6×，**不值得实现**；
USM 是唯一有效的部分，但 +143ms/页 + 40% 流量，性价比低于客户端 AGSL。

## 4. 方案矩阵

| 方案 | 覆盖 | 边缘提升 | 成本 | 结论 |
|---|---|---|---|---|
| 不动 | — | — | — | 1.04× 下本来就够 |
| 服务端 Lanczos+USM | 全设备 | +8~14% | 143ms/页、+40% 流量 | 不划算 |
| AGSL cubic（自绘） | **33+** | +14.5% | +1ms GPU | 可选，需改渲染 |
| AGSL 锐化（不改几何） | 33+ | 未测 | 低 | 最小可用方案 |
| native 重采样（NDK） | 全 | ≈ AGSL | 构建链变更 | D 成功后可跳过 |
| **ncnn/ORT 模型** | 高 | **+140%** | 1.2s/页（桌面 GPU） | 观感质变，内容会变 |
| AGSL 完整 Anime4K | — | — | — | **结构上不可行** |

## 5. 建议路线

若最终要做，按此顺序：

1. **只在 `scale > 1.5` 时启用**（正常阅读零开销、零风险）。
2. **先做 AGSL 单 pass 锐化**（不改采样几何，不必自绘、不必处理首帧失效）。
3. 模型档作为「增强模式」开关，默认关；算完落盘缓存，失败静默退回原图。

## 6. 风险

- **AI 超手会改内容**：网点、拟声字。必须用真实漫画页验收，且征得用户同意（开关默认关）。
- **自绘方案的首帧空白**：`LazyColumn` 第一项在挂 `renderEffect` 后首帧不渲染，
  现有 `AsyncImage` 没有这个问题，改自绘要专门处理。
- **AGSL 只覆盖 API 33+**，30–32 只能退回双线性。
- **流量**：服务端放大 +40%，只在"源宽 < 目标宽"时触发可控量。

### 若要重建探针（先读 §1 再决定值不值）

1. 新建 `android/app/src/debug/`，放一个 `ProbeActivity`（manifest 里 `exported=true`），
   用 `Modifier.graphicsLayer { renderEffect = ... }` 挂 AGSL 效果；
   源图从 `getExternalFilesDir()/probe_src.png` 读，缺失时用合成样张。
2. **四行对照必须有** —— 双线性 / 原图 1:1 / cubic 直接入层 / cubic 原生入层，
   其中「直接入层 vs 原生入层」是判断 shader 能否拿到原生像素的唯一手段（见 §3.5）。
3. 抓图**不要用 `captureToImage`**（在带 renderEffect 的图层上会丢内容，实测前两行变空白/条纹），
   用 `adb exec-out screencap -p` 抓整屏再按节点边界裁。

## 8. 同类方案调研

调研过一圈同类实现，只记做法与结论：

| 做法 | 参考价值 |
|---|---|
| native Lanczos3 / CatmullRom 1.5/2/2.5/3× + 神经网络模型 | 产品形态最完整；Anime4K 只是早期轻档 |
| Vulkan / 高通·联发科 NPU，结果落缓存，失败保留原图 | 调度与降级策略可借鉴 |
| 提供 5 种缩放算法可选（含 Lanczos3） | 能选的必然自绘，Compose 系做不到 |
| 固定双线性，相关优化诉求长期悬置 | 反证：这条路一直没人做通 |
| 反向代理拦截图片做超分，`size_threshold` 跳过 | 服务端方案天花板（要 Vulkan） |
| 入库时批量超分，离线模型预处理 | 要 CUDA，本机不可行 |

共同结论：**画质提升的可选空间都来自自绘/SurfaceFlinger 级别**，Compose 的
`FilterQuality` 只能表达「不过滤 / 过滤」，不存在算法可选这一档。
